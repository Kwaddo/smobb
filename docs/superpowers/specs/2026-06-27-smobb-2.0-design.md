# S.M.O.B.B. 2.0 — Design

**Date:** 2026-06-27
**Status:** Approved (architecture + phasing)

## Summary

S.M.O.B.B. is a text-based mystery/horror narrative game, originally written in
Java (~2,300 lines across 12 classes in `src/com/company/`). This project ports
it to Rust, separates all narrative text from program logic, audits the story for
gaps and defects, and ships it as a terminal-styled application across desktop,
web, and mobile browsers.

## The four goals → how each is met

1. **Java → Rust** — full port into a Rust workspace (pure engine crate + frontends).
2. **Separation of texts/guides** — all dialogue leaves the code and becomes
   **data files** (RON); the engine becomes pure logic; the in-game guide and
   recap notebook are redesigned to render in-terminal.
3. **Missing story** — a written story audit (`story-audit.md`, Phase 0) plus
   auto-fix of clear defects; larger narrative arcs are flagged for the author.
4. **All-platform terminal app** — native ratatui TUI (desktop) + WASM/xterm.js
   (web + mobile browser, installable as a PWA).

## Source-of-truth understanding

- **Hub** (`Main`) reads names/passwords/commands → dispatches to character scenes.
- **Character classes** (`Ali`, `Bader`, `Bevil`, `Hasan`, `Josh`, `Qassim`,
  `Smobb`) each run a `do/while` loop, `switch` on input, print color-coded,
  time-delayed dialogue.
- **`Bits`** — ANSI color per speaker, `PS()` (print + sleep), `TD()`/`WTD()`
  (dramatic `...`), global `interval` + `skipMode`.
- **`Extra`** — 12 abstract parable "stories".
- **`Ending`** — final monologue + save/die choice.
- **`Guide`** — in-game help (names / play / recap / settings); play guide uses
  Swing `JOptionPane` PNG popups.
- **`recap.txt` / `truerecap.txt`** — clue "notebook" (currently broken; see audit).

### Story core
A friend group (Hasan, Bader, Qassim, Bevil, Ali, + hired Josh) builds a
fast-learning AI "Jaffar" that feeds off Bader's "Tranava files" (an archive about
Ali). Jaffar turns malicious and drives a chain of deaths (Qassim murdered by a
mind-controlled Bader; Ali burns the lair). Ali fuses an incomplete Jaffar/SMOBB
with Qassim's uploaded brain to create **M.A.V.I.S.** — which is the player: a
time-looping "god"/husk of Qassim replaying these recordings. Jaffar speaks in
hexadecimal.

## Architecture — Rust workspace

```
smobb/
├─ crates/
│  ├─ smobb-core/   # pure engine: no I/O. content loader + step machine + tests
│  ├─ smobb-tui/    # native binary: ratatui/crossterm driver
│  └─ smobb-wasm/   # cdylib: wasm-bindgen driver
├─ web/             # xterm.js host + vite + PWA manifest
├─ content/         # *.ron scene files (ALL story text lives here)
└─ docs/superpowers/specs/
```

**Principle:** content (data) ↔ engine (logic) ↔ drivers (I/O) are fully
separated. That separation is goal #2.

### Engine model (`smobb-core`)

The game is a state machine. A **Location** (the hub, or a character) holds a map
of `command → Scene`. A **Scene** is an ordered list of `Step`s:

- `Line { speaker, text }` — the speaker enum maps to a color automatically,
  eliminating per-line color prefixing.
- `Pause` — the `...` dramatic beat (old `TD`/`WTD`).
- `Prompt { branches: input → target }` — handles nested choices
  (e.g. Ali `7549009` → yes/no → name check).
- `Recap { text }` — append a clue to the notebook.
- `Goto` / `Return`.

The engine is **pure and non-blocking**: `advance(input) -> Vec<Output>`, where
`Output ∈ { Styled(line), Sleep(ms), AwaitInput, RecapWrite, End }`. The host
loop owns timing and input. This is the key portability fix — the Java original
bakes `Thread.sleep` into its core, which is exactly what prevents a web port. One
pure engine therefore serves both the blocking TUI and the async web host.

### Content format — RON

RON (Rust Object Notation): typed, enum-friendly, ideal for a branching scene
graph. Example:

```ron
Scene("qassim_final", [
  Line(Qassim, "Ali. This voice message would probably be my last."),
  Line(Qassim, "I hear noises, and I'm scared. The police are 20 minutes away."),
  Recap("The password for S.M.O.B.B.'s files is '9285005'."),
  Pause,
])
```

The speaker → ANSI color table lives in one place (port of `Bits`). Content is
embedded into the binary/WASM artifact at build time (no loose files to ship).

### Drivers

- **TUI** (`smobb-tui`): crossterm raw mode, scrolling transcript pane + input
  line, 24-bit color, `Sleep` → `thread::sleep`, recap → local file. Settings
  (interval / skipmode) preserved.
- **Web** (`smobb-wasm` + `web/`): engine compiled to WASM; xterm.js renders;
  `Sleep` → `setTimeout`; recap → `localStorage`; PWA manifest makes it
  installable on iOS/Android home screens. Same colors, same feel.
- A small `Host` trait abstracts storage + clock so the engine never knows which
  platform it runs on.

### Guide + recap redesign (goal #2, experience)

- **Drop the Swing PNG popups** (`guide1-3.png`, `JOptionPane`) — they break the
  terminal goal and are unavailable headless/web. Replace with an in-terminal
  text guide (`names / how-to-play / settings / recap`). PNGs may be kept as an
  optional web `?` overlay, but text is the default.
- **Fix recap** — proper append + dedup notebook with an in-app viewer and a
  clear command. (The Java version opens `recap.txt` in truncate mode at the top
  of 7 methods, wiping the notebook on nearly every visit, and the reader uses a
  `new String[10000000]` array with a broken nested loop.)
- Consistent hub help / shortcut listing.

## Phases (each later phase gets its own implementation plan)

- **Phase 0** — Story audit → `docs/superpowers/specs/2026-06-27-smobb-story-audit.md`.
  Auto-fix clear defects (cutoff line, package-name leak, typos).
- **Phase 1** — Extract all text → `content/*.ron` (verbatim + the approved defect fixes).
- **Phase 2** — `smobb-core` engine + content loader + tests.
- **Phase 3** — `smobb-tui` native frontend.
- **Phase 4** — `smobb-wasm` + `web/` + PWA.
- **Phase 5** — Packaging (desktop binaries, web deploy).

This spec covers the whole architecture. The first implementation plan targets
**Phase 0–2** (audit, content model, engine). Phases 3–5 get follow-on plans.

## Decisions locked

- Platform: Rust core → native ratatui TUI (desktop) + WASM/xterm.js (web + mobile browser).
- Story gaps: audit + fix only clear defects; flag larger arcs for the author.
- Text fidelity: verbatim + fix clear errors; content moves to data files (no style rewrite).
- Content format: RON.
- Guide: in-terminal text (PNG popups dropped from default).
